# Vector Database from Scratch

## What we are building
A pure-Python vector database and nearest-neighbor search engine. It will eventually feature both an exact brute-force search index and a custom approximate nearest neighbor (ANN) index based on HNSW logic, complete with measurements and benchmark plots for speed-vs-accuracy trade-offs.

## Why no existing libraries?
The project strictly prohibits standard vector database solutions (Pinecone, Chroma) and search algorithms (FAISS, `sklearn.neighbors`). Relying on off-the-shelf imports obscures the mathematical and algorithmic foundation of modern AI retrieval. Building it entirely with NumPy ensures a deep, foundational understanding of high-dimensional spatial indexing, metric spaces, and performance trade-offs. 

## What this stage does
This is the foundational stage. It programmatically generates a deterministic, semantically rich dataset of 50,000 texts, utilizes a lightweight local embedding model to map these texts into vector space, normalizes them, and persists the raw arrays and metadata to disk.

## Stage 2: Exact Nearest-Neighbor Index
We have built an **Exact Brute-Force Index** to act as our foundational Ground Truth. 

* **What it is:** An index that holds all dataset vectors and performs a literal exhaustive mathematical comparison against every single one of them to answer a query. 
* **Why no libraries?** Using FAISS, Pinecone, or Chroma hides the complex math required for similarity search. We implemented it purely in NumPy.
* **Why it is allowed to be slow:** It guarantees 100% mathematical correctness. It does not use approximations. As our dataset grows, checking every vector linearly degrades performance ($O(N)$). 
* **Ground Truth:** When we build our HNSW approximation index later, it will make guesses to achieve speed. We will benchmark the HNSW's *Recall* (accuracy) by comparing its fast answers against the slow, flawlessly accurate answers generated by this Exact Index.
* **Metric Used:** **Cosine Similarity**. Because our Embedding Pipeline explicitly $L_2$ normalizes the vectors to length 1, we can calculate Cosine Similarity via a highly optimized Dot Product (`np.dot`).

## Stage 3: HNSW Approximate Index
We implemented a custom Hierarchical Navigable Small World (HNSW) graph to perform Approximate Nearest Neighbor (ANN) search.

* **Conceptual Design:** Instead of checking every vector, HNSW structures data like a highway network. High layers are "interstates" connecting distant clusters. Layer 0 contains "local roads" connecting every single point. Searches drop from the interstate to local roads, skipping over 99% of the dataset geometry.
* **Why it's approximate:** By hopping through connections, it might take a suboptimal path and miss the absolute closest point. It trades guaranteed exactness for massive speed gains.
* **M Parameter:** The maximum number of local connections a node can make. High `M` creates a denser graph (more accurate, uses more RAM).
* **ef_construction:** Controls how broadly the algorithm searches for good neighbors *while building the graph*. 
* **ef_search:** Controls the breadth of the search candidate queue *during querying*. This acts as our primary **Speed vs. Accuracy Tradeoff Knob**. 
* **Lazy Deletion:** When a node is deleted, we just add its internal ID to a `deleted` Set rather than physically rebuilding the graph connections. During search, the algorithm can still travel *through* the deleted node to find its neighbors, but filters it out of the final returned results.
